6.1 Supervised machine learning: Basic framework, regression models and classification models

Let’s understand term machine learning. According to Dave Bergmann of IBM, Machine learning is a subset of AI where algorithms learn patterns from training data to make inferences about new data without explicit instructions. This pattern recognition ability enables machine learning models to make decisions or predictions without explicit, hard-coded instructions.

Though “machine learning” and “artificial intelligence” are often used interchangeably, they are not quite synonymous. In short: all machine learning is AI, but not all AI is machine learning.

Machine learning works through mathematical logic. The relevant characteristics (or “features”) of each data point must therefore be expressed numerically, so that the data itself can be fed into a mathematical algorithm that will “learn” to map a given input to the desired output. The (often manual) process of choosing which aspects of data to use in machine learning algorithms is called feature selection. Feature extraction techniques refine data down to only its most relevant, meaningful dimensions.

6.2 Types of machine learning

All machine learning methods can be categorized as one of three distinct learning paradigms: supervised learning, unsupervised learning or reinforcement learning, based on the nature of their training objectives and (often but not always) by the type of training data they entail.

Supervised learning trains a model to predict the “correct” output for a given input. It applies to tasks that require some degree of accuracy relative to some external “ground truth,” such as classification or regression. Unsupervised learning trains a model to discern intrinsic patterns, dependencies and correlations in data. Unlike in supervised learning, unsupervised learning tasks don’t involve any external ground truth against which its outputs should be compared.

Reinforcement learning (RL) trains a model to evaluate its environment and take an action that will garner the greatest reward. RL scenarios don’t entail the existence of a singular ground truth, but they do entail the existence of “good” and “bad” (or neutral) actions.

6.2.1 Supervised learning

Supervised learning algorithms train models for tasks requiring accuracy, such as classification or regression. Supervised machine learning powers both state-of-the-art deep learning models and a wide array of traditional ML models still widely employed across industries.

Regression models predict continuous values, such as price, duration, temperature or size. Examples of traditional regression algorithms include linear regression, polynomial regression and state space models.

Classification models predict discrete values, such as the category (or class) a data point belongs to, a binary decision or a specific action to be taken. Examples of traditional classification algorithms include support vector machines (SVMs), Naïve Bayes and logistic regression.

Many supervised ML algorithms can be used for either task. For instance, the output of what’s nominally a regression algorithm can subsequently be used to inform a classification prediction.

6.4 Data Pre-Processing

Data pre-processing is necessary before building model. In Sea urchin case study we have a perfect data set hence we could straight away jump to model building however it is not the case everytime. You will get messy data most of the time. You need to process the messy data into a polished and organized before building any model. Package recipes is the R package we will use to process the data. So, let’s begin.

The package Recipes has inbuilt series of preprocessing steps, such as:

  • Converting qualitative predictors to indicator variables (also known as dummy variables),

  • Transforming data to be on a different scale (e.g., taking the logarithm of a variable),

  • Transforming whole groups of predictors together,

  • Extracting key features from raw variables (e.g., getting the day of the week out of a date variable),

6.4.2 Build the preprocessing recipe

This is the core of the exercise: every cleaning/encoding Decision is captured as a recipe step, learned only on the training set, then reproducibly applied to any new data.

soy_recipe <-
  recipe(Class ~ ., data = soy_train) |>
 
  # (a) Drop predictors that are (near) constant -> add no signal
  step_nzv(all_predictors()) |>
 
  # (b) Handle missing values in categorical predictors
  #     Bagged trees impute using the other predictors' patterns,
  #     which works well for structured agronomic survey data.
  step_impute_bag(all_nominal_predictors(), impute_with = imp_vars(all_predictors())) |>
 
  # (c) Collapse rarely-occurring factor levels into "other"
  #     (prevents unstable dummy columns from very rare categories)
  step_other(all_nominal_predictors(), threshold = 0.03, other = "other_level") |>
 
  # (d) Ensure factor levels seen in test/new data don't break the model
  step_novel(all_nominal_predictors()) |>
 
  # (e) One-hot / dummy encode categorical predictors for models
  #     that need numeric input
  step_dummy(all_nominal_predictors(), one_hot = TRUE) |>
 
  # (f) Remove any dummy columns that are (still) near-zero variance
  #     after encoding
  step_nzv(all_predictors()) |>
 
  # (g) Remove highly correlated dummy columns (redundant info)
  step_corr(all_numeric_predictors(), threshold = 0.9) |>
 
  # (h) Scale numeric predictors (harmless here, essential if you
  #     later add real-valued agronomic measurements e.g. rainfall_mm)
  step_normalize(all_numeric_predictors()) |>
 
  # (i) Address class imbalance (19 disease classes, some very rare)
  #     using up-sampling on the TRAINING data only
  step_upsample(Class, over_ratio = 0.5)

## Per-class AUC (one-vs-rest)
## a multiclass setting we loop over each class, re-code it as a
## binary "this class vs. all others" problem, and score that.
class_levels <- levels(soy_probs$Class)
 
roc_auc_by_class <- map_dfr(class_levels, function(cls) {

    levels = c(cls, "other")   # cls = "event" / first level

    truth = truth,

6.4.8 Concluding Remarks

This analysis demonstrated an end-to-end multiclass classification pipeline for diagnosing soybean diseases from categorical agronomic and environmental observations. The recipes package handled the preprocessing burden reproducibly and without data leakage — filtering near-zero-variance predictors, imputing missing symptom records via bagged trees, pooling rare factor levels, one-hot encoding, removing redundant correlated features, and upsampling rare disease classes — all learned strictly on the training split and applied identically to the held-out test data.

The random forest classifier trained on this preprocessed data was evaluated using one-vs-rest ROC curves for each disease class rather than a single aggregate accuracy figure, since accuracy alone can mask poor performance on rarer or harder-to-distinguish diseases. Per-class AUC values reveal which diseases the model separates cleanly from all others (curves hugging the top-left corner, AUC near 1.0) versus which ones it confuses with visually or symptomatically similar conditions (curves closer to the diagonal, AUC near 0.5). This class-by-class view is more actionable for an agribusiness context than a single overall score — it tells you specifically which diseases a field-deployed diagnostic tool can be trusted on, and which would still need expert/agronomist confirmation before acting on the model’s flag.

Practical takeaway: the preprocessing recipe is reusable well beyond this dataset — swap in real farm records (soil tests, weather logs, crop-cam imagery-derived features, past yield data) and the same step_impute_* → step_other/step_novel → step_dummy → step_corr/step_nzv → step_normalize → step_upsample sequence provides a robust, leakage-free foundation for any agribusiness classification problem — whether that’s disease diagnosis, loan-default risk for agri-lending, or yield-grade prediction.

The test RMSE of 372.64 kg/hectare represents the typical magnitude of error when the multiple regression model predicts crop yield on data it has not seen before (the held-out test set).   • The training-set residual standard error was 283.5 kg/hectare — noticeably lower than the test RMSE of 372.64.

  • This gap (283.5 vs. 372.64) is a signal worth flagging: the model fits the training data better than it generalizes to new data. Some of this is expected (models almost always perform somewhat worse on unseen data), but a gap this size also lines up with what you found in the coefficient output — temperature was included as a plain linear term even though its true relationship with yield is quadratic (peaking at an optimal temperature). Because the model can’t capture that curvature, it likely makes systematically larger errors on test observations with temperatures far from the training set’s typical range, inflating the test RMSE.

  • To assess whether 372.64 kg/hectare is “good” or “bad,” it should be compared against the scale of the outcome itself — e.g., as a percentage of mean yield (mean(train$yield_kg_ha) would give you that denominator). A RMSE that’s small relative to typical yield (say, under 10%) suggests reasonably useful predictions for advisory purposes; one that’s large relative to typical yield suggests the model isn’t precise enough to act on without caution.

  • This is exactly the kind of gap the polynomial regression step (correctly modeling temperature’s curvature) should help close — comparing this multiple-regression test RMSE against the polynomial model’s test RMSE would be a natural next check, and a good addition to your assignment’s Part C if you want students to explicitly connect “which model generalizes best” rather than just “which model fits training data best.”

A polynomial regression model was estimated to test whether allowing temperature a curved (quadratic) relationship with yield would improve on the purely linear multiple regression model. The polynomial model was statistically significant, F(5, 154) = 130.50, p < .001, and explained substantially more variance in yield than the linear multiple regression model, R² = .809, adjusted R² = .803, compared to R² = .645, adjusted R² = .636 previously.

The quadratic term for temperature was highly significant, b = −2412.82, SE = 209.60, t(154) = −11.51, p < .001, while the linear temperature term was not, b = 11.13, SE = 211.05, t(154) = 0.05, p = .958. This pattern confirms what the earlier linear model’s non-significant temperature coefficient had obscured: temperature does meaningfully affect yield, but through a curved, not straight-line, relationship — consistent with an agronomic optimum temperature, where yield is highest at a moderate temperature and declines when conditions are either too cool or too hot. The negative sign on the squared term indicates an inverted-U (concave-down) curve, as expected.

Rainfall, b = 2.47, SE = 0.12, t(154) = 20.64, p < .001, fertilizer, b = 2.57, SE = 0.44, t(154) = 5.87, p < .001, and soil pH, b = 291.51, SE = 32.89, t(154) = 8.86, p < .001, all remained significant positive predictors, with coefficient estimates very similar to the linear multiple regression model — indicating their linear effects on yield were already well-captured and are not confounded with temperature’s curvature.

The residual standard error also dropped notably, from 283.5 kg/hectare (linear multiple regression) to 208.6 kg/hectare (polynomial), reflecting a considerably tighter fit to the training data once temperature’s true functional form was correctly specified.

Practical takeaway: This is a clean illustration of a common modeling mistake — a predictor can appear “non-significant” in a linear model not because it doesn’t matter, but because the model was given the wrong functional form to detect it. Once quadratic curvature was allowed, temperature emerged as one of the most important predictors in the model (via its squared term).

6.5.7 STEPWISE REGRESSION

When we build model we use a set of predictors. All predictors do not contribute to the model and still create noise and increases variance. Here, we use STEPWISE REGRESSION which automatically selects a subset of predictors by adding/removing predictors to optimize AIC (lower = better trade-off of fit vs. complexity).

full_model <- lm(yield_kg_ha ~ rainfall_mm + fertilizer_kg + temperature_C + soil_ph,
                  data = train)
null_model <- lm(yield_kg_ha ~ 1, data = train)

step_model <- stats::step(
  null_model,
  scope = list(lower = null_model, upper = full_model),
  direction = "both",   # "forward", "backward", or "both"
  trace = FALSE
)

This is expected: adjusted R² penalizes unnecessary predictors, and since temperature’s linear term was non-significant in the full model (p = .934, from your earlier output), removing it slightly improves the fit efficiency without sacrificing explanatory power.

Important caveat worth flagging (especially for a student assignment): this result illustrates a key limitation of stepwise selection rather than a genuine insight about temperature’s importance. Temperature was correctly dropped as a linear term, but your polynomial regression model showed temperature’s quadratic term was highly significant (p < .001) and substantially improved fit (adjusted R² = .803). Stepwise selection using step() only ever considered rainfall, fertilizer, temperature, and soil pH as linear terms — it never had the opportunity to discover the curved relationship, because poly(temperature_C, 2) was never in its candidate scope. This is a classic pitfall of stepwise/AIC-based selection: it can only select among the functional forms you explicitly offer it, and will confidently discard a genuinely important predictor if its true effect doesn’t match the form tested.

Practical takeaway: stepwise regression is useful for pruning redundant linear predictors efficiently, but it is not a substitute for exploring nonlinear relationships first (via EDA plots or domain knowledge) — a variable dropped by stepwise selection may still be highly important if given the right functional form, as shown here.
